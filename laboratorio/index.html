Antes de empezar

Cómo trabajar los ejercicios

Todos siguen el mismo formato:

  1. Situación: un caso real y sencillo (una web, una lista, unos apuntes).
  2. Tareas: qué tienes que conseguir. Intenta resolverlo tú primero.
  3. Solución (desplegable): comandos con un comentario muy breve y la salida que deberías ver.

La regla de oro de estas prácticas: mira antes y después. Lanza git status y git log --oneline al empezar, después de cada cambio importante y al terminar.

Cómo leer los bloques de código

# Esto es un comentario: explica el paso
git status -sb                  # comando (lo que escribes)
│ ## main...origin/main [ahead 1]
│ (esto es la salida esperada; el botón Copiar no la copia)

Las salidas están en inglés, como en una instalación por defecto de Git Bash. Los hashes (9a9bb7a) serán distintos en tu equipo: usa los tuyos.

Carpeta de prácticas. Trabaja siempre dentro de ~/practicas-git, una subcarpeta por ejercicio. Si algo se rompe, bórrala y empieza de nuevo.
Remoto sin GitHub. Los ejercicios de equipo y conflictos usan un repositorio bare local que simula el servidor: así dos "alumnos" (dos carpetas) pueden chocar en tu mismo equipo. Se prepara en el ejercicio de --bare.
⚠️ Destructivo. Los comandos marcados con ⚠️ borran trabajo o reescriben el historial. Antes de lanzarlos, lee el comentario.
Terminal. Windows: Git Bash (se instala con Git). Linux: la terminal normal. Los comandos son los mismos.

Unidad 1

Conceptos mínimos para entender Git

Casi todos los errores con Git vienen de no saber en qué zona está un cambio. Antes de los ejercicios, el mapa.

  • Las cuatro zonas y los comandos que mueven cambios entre ellas
  • Estados de un archivo y cómo leer git status -s
  • Commits, HEAD, ramas y origin/main
  • Simulador: prueba los comandos sin miedo
1.1

Las cuatro zonas

Working directory tu carpeta

Los archivos tal como los editas. Aquí trabajas.

Staging (index) preparado

Lo que entrará en el próximo commit. Una "foto" en preparación.

Repositorio local .git

El historial de commits, guardado en la subcarpeta oculta .git.

Remoto origin

La copia en GitHub o en un servidor. Se sincroniza a mano.
git add →
git commit →
git push →
← git pull / fetch
← git restore
← git restore --staged
← git reset
git clone ↓ (todo)
Idea clave. git commit no guarda "lo que hay en tu carpeta": guarda lo que hay en staging. Por eso existe git add.
Local vs remoto. Commit, reset, revert, ramas… todo ocurre en tu equipo. Solo push, pull, fetch y clone hablan con el remoto.
1.2

Estados de un archivo y git status -s

git status explica el estado con frases; git status -s lo resume en dos columnas:

  • Columna izquierda: estado en staging.
  • Columna derecha: estado en el working directory.

git status -sb añade una primera línea con la rama y si vas por delante (ahead) o por detrás (behind) del remoto.

│ M  index.html
│  M estilos.css
│ ?? notas.txt

1.3

Commits, HEAD, ramas y origin/main

  • Commit: una foto del proyecto con autor, fecha, mensaje y un hash (a1b2c3d). Cada commit apunta a su padre.
  • Rama (main, login): una simple etiqueta móvil que apunta a un commit. Al hacer commit, avanza.
  • HEAD: "dónde estás ahora". Normalmente apunta a la rama actual.
  • origin/main: cómo estaba main en el remoto la última vez que hiciste fetch/pull/push. No se actualiza sola.
  • HEAD~1 es el commit anterior a HEAD; HEAD~2, dos atrás.
  • Upstream: rama remota vinculada a tu rama (push -u). Permite usar git push y git pull sin argumentos.
1.4 · Simulador de zonas (1/3)

Del editor a GitHub: el viaje de un cambio

Un proyecto con un único archivo, index.html. Pulsa ▶ Siguiente paso y observa en cada paso qué zona cambia (se resalta), la explicación y el comando real que lo haría en la terminal. No hace falta escribir nada.

Cómo leerlo. Las cuatro cajas son las cuatro zonas de Git, de izquierda a derecha: lo que editas → lo preparado → lo guardado en tu PC → lo subido. Cada versión del archivo tiene un nombre (v1, v2…) para que veas dónde está cada una.
1.4 · Simulador de zonas (2/3)

Deshacer: cada comando actúa sobre una zona distinta

restore toca la carpeta o staging; reset mueve la rama hacia atrás (y según la opción arrastra staging y carpeta); revert añade un commit nuevo. Sigue el recorrido y compara qué zonas se resaltan en cada caso.

1.4 · Simulador de zonas (3/3)

Guardar a medias, recuperar lo perdido y forzar con seguridad

stash aparta cambios para poder actualizarte, reflog encuentra commits que ya no salen en el log y --force-with-lease sobrescribe el remoto solo si nadie ha subido nada que no hayas visto.

Configuración

Configurar Git por primera vez

Situación. Acabas de instalar Git en el portátil de clase. Antes de hacer ningún commit, Git necesita saber quién eres y cómo quieres que se comporte.

Tareas.

  1. Comprueba la versión instalada y la configuración actual.
  2. Configura tu nombre y correo (el mismo que en GitHub).
  3. Haz que las repos nuevas usen main, el editor sea nano y git pull fusione con merge.
  4. Revisa la configuración y en qué archivo se ha guardado.
Comandosgit --versiongit config
Tres niveles. --system (todo el equipo) → --global (tu usuario, ~/.gitconfig) → --local (solo esa repo, .git/config). Gana el más específico.
¿Por qué pull.rebase? Desde Git 2.33, si local y remoto han divergido y no está configurado, git pull se para con fatal: Need to specify how to reconcile divergent branches.
Solución (intenta primero) 
git --version
│ git version 2.43.0
git config --list                                      # configuración actual (puede estar casi vacía)

git config --global user.name "Juan Carlos San Román"
git config --global user.email "tu_email@ejemplo.com"
git config --global init.defaultBranch main            # repos nuevas con rama main, no master
git config --global core.editor "nano"                 # editor para mensajes, rebase -i, merges
git config --global pull.rebase false                  # git pull = fetch + merge
git config --global core.autocrlf false                # Git no toca los finales de línea (ver unidad 11)

git config --list --show-origin                        # todo, indicando el archivo de cada valor
│ file:/home/ana/.gitconfig   user.name=Juan Carlos San Román
│ file:/home/ana/.gitconfig   init.defaultbranch=main
git config user.name                                   # consultar un solo valor
│ Juan Carlos San Román

Situación. La web genera logs/app.log y tiene un .env con la contraseña de la base de datos. Además, hace días subiste por error debug.log, que ya está en el repositorio.

Autenticarse con GitHub

GitHub no acepta la contraseña de la cuenta desde la terminal. Hay dos caminos: SSH (clave pública/privada) o HTTPS con un token.

  • SSH: git@github.com:usuario/repo.git
  • HTTPS: https://github.com/usuario/repo.git
  • Cambiar de uno a otro con git remote set-url
  • Aulas que se reinician: guardar y restaurar la configuración
Autenticación

Conectar Git con GitHub por SSH

Situación. No quieres escribir credenciales en cada push. Vas a crear una pareja de claves en tu equipo y registrar la pública en GitHub.

  1. Genera una clave ed25519 con tu correo.
  2. Cárgala en el agente SSH.
  3. Copia la clave pública y regístrala en GitHub.
  4. Prueba la conexión.
Comandosssh-keygenssh-agentssh-addssh -T
En GitHub: avatar → Settings → SSH and GPG keys → New SSH key. Título que identifique el equipo (p. ej. "Portátil clase") y pega la clave pública.
Nunca compartas id_ed25519 (sin .pub): es la clave privada.
Solución 
ssh-keygen -t ed25519 -C "tu_email@ejemplo.com"     # Enter para la ruta por defecto; passphrase opcional
ls -l ~/.ssh/
│ id_ed25519        ← privada
│ id_ed25519.pub    ← pública
eval "$(ssh-agent -s)"                              # arranca el agente
│ Agent pid 1234
ssh-add ~/.ssh/id_ed25519                           # añade la PRIVADA al agente
cat ~/.ssh/id_ed25519.pub                           # muestra la PÚBLICA: cópiala en GitHub
│ ssh-ed25519 AAAAC3Nza...  tu_email@ejemplo.com
ssh -T git@github.com                               # prueba (la 1ª vez responde "yes")
│ Hi usuario! You've successfully authenticated, but GitHub does not provide shell access.
ssh-keygen -t ed25519 -C "tu_email@ejemplo.com"
# Como administrador, activar el agente una sola vez:
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519            # la PRIVADA
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard   # la PÚBLICA al portapapeles
ssh -T git@github.com

HTTPS con token y cambio de HTTPS a SSH

Situación. En el ordenador del aula no puedes usar SSH (puerto 22 cerrado). Usarás HTTPS. Más tarde, en casa, quieres cambiar esa misma repo a SSH.

  1. Crea un token en GitHub y úsalo como contraseña al hacer push.
  2. Haz que Git recuerde la credencial.
  3. Comprueba la URL del remoto y cámbiala a SSH.
Comandosgit clone https://…credential.helpergit remote -vgit remote set-url
Token en GitHub: Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token. Elige la repo, permiso Contents: Read and write y una caducidad. Cópialo: solo se muestra una vez.
Windows: Git for Windows instala Git Credential Manager, que abre el navegador para iniciar sesión y guarda la credencial solo.
Solución 
git clone https://github.com/usuario/web-tienda.git
cd web-tienda
git push                                           # al pedir credenciales:
│ Username for 'https://github.com': usuario
│ Password for 'https://usuario@github.com':       ← pega el TOKEN, no tu contraseña

git config --global credential.helper store        # Linux: guarda la credencial (texto plano en ~/.git-credentials)
git config --global credential.helper "cache --timeout=3600"   # alternativa: solo en memoria 1 hora

git remote -v                                      # situación inicial
│ origin  https://github.com/usuario/web-tienda.git (fetch)
│ origin  https://github.com/usuario/web-tienda.git (push)
git remote set-url origin git@github.com:usuario/web-tienda.git
git remote -v                                      # situación final
│ origin  git@github.com:usuario/web-tienda.git (fetch)
│ origin  git@github.com:usuario/web-tienda.git (push)
git push                                           # ahora usa la clave SSH

No perder la configuración de Git y SSH en un aula que se reinicia

Situación. En el aula, la unidad C: se restaura en cada reinicio: se pierden ~/.gitconfig (identidad, alias) y ~/.ssh/ (claves). La unidad D: se conserva. En D:/git-scripts tienes dos scripts: guardar-config.sh y restaurar-config.sh.

  1. Guarda tu configuración en D:/git_backup y comprueba qué se ha copiado.
  2. Simula el reinicio con reiniciar-equipo y comprueba que Git ya no sabe quién eres y que SSH falla.
  3. Restaura y verifica user.name y ssh -T git@github.com.
Comandosbash guardar-config.shbash restaurar-config.shcat ~/.gitconfigcp -r

En Git Bash, D:/git_backup y /d/git_backup son la misma carpeta. Los scripts están en apuntes/recursos/scripts.

Unidad 6

Deshacer cambios

Elegir bien depende de dos preguntas: ¿en qué zona está el error? y ¿ya lo he subido?

  • restore: archivos de la carpeta y del staging
  • commit --amend y reset: commits que aún no has subido
  • revert: commits ya subidos (sin reescribir historial)
  • reflog: la red de seguridad
6.0 · Mapa de decisión

¿restore, reset o revert?

restore Archivos. Devuelve un archivo a como estaba en staging o en un commit. No toca el historial.
reset Mueve la rama hacia atrás. --soft conserva los cambios en staging, mixto (por defecto) en la carpeta, --hard ⚠️ los borra. Reescribe el historial.
revert Añade un commit nuevo que hace lo contrario de otro. El historial solo crece: seguro con commits compartidos.
Quiero…¿Subido?Uso
Descartar cambios de un archivo no añadido—git restore f ⚠️
Sacar un archivo de staging—git restore --staged f
Recuperar un archivo de un commit antiguo—git restore --source=<hash> f
Corregir mensaje o añadir algo al último commitNogit commit --amend
Deshacer commits conservando el trabajoNogit reset --soft / git reset
Tirar commits y su trabajoNogit reset --hard ⚠️
Deshacer un commit que ya tienen otrosSígit revert <hash>
Quitar un commit subido, trabajando soloSíreset --hard + push --force-with-lease ⚠️
Recuperar algo tras un reset o borrar una rama—git reflog

Resolver conflictos

Un conflicto ocurre cuando dos líneas de trabajo cambian las mismas líneas de un archivo. Git no elige por ti: marca el archivo y espera.

  • Leer las marcas de conflicto
  • Conflicto entre dos ramas locales
  • Quedarse con una versión entera
  • Push rechazado: pull con merge o con rebase
  • Ganar el remoto o ganar el local
8.0

Anatomía de un conflicto

Lista de la compra
<<<<<<< HEAD
- pan de molde
=======
- pan integral
>>>>>>> origin/main
MarcaSignifica
<<<<<<< HEADEmpieza tu versión (rama actual)
=======Separador
>>>>>>> otraTermina la versión que llega

Receta en 4 pasos

  1. git status: localiza los archivos en both modified.
  2. Edita cada archivo: deja el contenido correcto y borra las tres marcas.
  3. git add archivo: marca el conflicto como resuelto.
  4. Termina la operación: git commit (merge), git rebase --continue, git cherry-pick --continue o git revert --continue.
¿Te has liado? git merge --abort / git rebase --abort lo deja todo como antes de empezar.
En un rebase los papeles se invierten: HEAD es la rama sobre la que te recolocas (lo remoto) y la otra parte es tu commit.
